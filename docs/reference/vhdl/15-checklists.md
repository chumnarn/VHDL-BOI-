## 1. วิธีใช้เช็กลิสต์

เช็กลิสต์ในบทนี้เรียงตามลำดับที่ควรทำ

1. ทำข้อ 2 (โครงสร้างไฟล์) ก่อน — เป็นข้อที่ตรวจได้เร็วที่สุดด้วยเครื่องมือ
2. ทำข้อ 3 ถึง 7 (RTL) ก่อนเริ่มเขียน testbench
3. ทำข้อ 8 (testbench) ก่อนรัน
4. ทำข้อ 9 (ก่อนส่งงาน) เมื่อทุกอย่างทำงานแล้ว
5. ทำข้อ 10 ถ้าโปรเจกต์มีทั้งสองภาษา

## 2. เช็กลิสต์โครงสร้างไฟล์

- [ ] ชื่อไฟล์เป็น ASCII เท่านั้น ไม่มีชื่อไทยหรืออักขระพิเศษ
- [ ] ไฟล์เป็น UTF-8 **ไม่มี BOM** (ตรวจด้วย `Format-Hex <file> | Select-Object -First 1`
      ต้องเห็น `2D 2D` หรือ `2F 2F` เป็นไบต์แรก)
- [ ] เว้นวรรค 2 ช่อง ไม่มีเลขท้ายบรรทัด (trailing whitespace)
- [ ] บรรทัดจบด้วย LF ไม่ใช่ CRLF (สำคัญกับไฟล์ stimulus ที่อ่านด้วย `std.textio`
      เพราะ `\r` จะติดท้ายบรรทัดและทำให้การอ่านข้อมูลผิดพลาด)
- [ ] ทุก design unit มี context clause ของตัวเองก่อนหนึ่งบรรทัด
- [ ] หัวไฟล์มีคอมเมนต์ภาษาไทยระบุ: ชื่อตัวอย่าง, วัตถุประสงค์, มาตรฐานภาษา,
      หมายเหตุเรื่อง synthesizability และสิ่งที่ตัวอย่างสอน
- [ ] package อยู่ในไฟล์ที่ลงท้ายด้วย `_pkg` และคอมไพล์ก่อนไฟล์ที่ใช้มัน
- [ ] ชื่อ entity/module และชื่อพอร์ต ตรงกับเวอร์ชัน Verilog ของโมดูลเดียวกัน

ตรวจ BOM และ trailing whitespace ในครั้งเดียว:

```bash
cd code/reference/vhdl
# ไฟล์ที่มี BOM (ต้องไม่มีผลลัพธ์)
grep -rlP '^\xEF\xBB\xBF' examples/ || echo "no BOM found"
# ไฟล์ที่มี trailing whitespace (ต้องไม่มีผลลัพธ์)
grep -rnP '[ \t]+$' examples/ || echo "no trailing whitespace found"
```

## 3. เช็กลิสต์ RTL

- [ ] มาตรฐานหลักคือ VHDL-2008 และต้องคอมไพล์ผ่าน `--std=02` ด้วย
- [ ] ไม่มี `ieee.std_logic_arith` ใช้ `ieee.numeric_std` เท่านั้น
- [ ] ไม่มี `process (all)` (ต้องระบุ sensitivity list ให้ชัดเจน)
- [ ] ไม่มี `std.env`, `to_hstring`, `to_ostring`, external names
- [ ] ไม่มี conditional variable assignment (`v := '1' when c else '0'`)
- [ ] generic ตั้งชื่อเป็น `UPPER_CASE`
- [ ] signal ภายในของโมดูลลงท้าย `_i`
- [ ] process ลงท้าย `_p`
- [ ] ชื่อ instance ลงท้าย `_inst` หรือขึ้นต้นด้วย `u_`
- [ ] ค่าคงที่ตั้งชื่อเป็น `UPPER_CASE`
- [ ] ทุก generic มีค่าเริ่มต้นที่ใช้งานได้จริง
- [ ] ไม่มี signal ที่ประกาศนอก process แล้วถูก assign ใน clocked process
      (ถ้าเป็น signal ที่ประกาศนอก process แล้ว assign ใน process จะกลายเป็น latch
      เว้นแต่จะตั้งใจให้เป็น latch)

ตรวจฟีเจอร์ที่ห้ามใช้:

```bash
cd code/reference/vhdl
grep -rn 'process (all)\|std\.env\|to_hstring\|std_logic_arith' examples/ \
  || echo "no forbidden VHDL-2008-only feature found"
```

## 4. เช็กลิสต์ combinational logic

- [ ] sensitivity list ครอบคลุมทุกอินพุตที่อ่านใน process
- [ ] กำหนดค่าเอาต์พุต **ครบทุก path** (ค่าเริ่มต้นก่อน `case` หรือ `when others`)
- [ ] ไม่มี latch โดยไม่ตั้งใจ — ตรวจด้วย `ghdl --synth` ทุกครั้ง
- [ ] ใช้ `variable` เก็บค่ากลางแล้ว assign ลง signal ทีเดียวท้าย process
- [ ] `case` ที่แปลงค่าเป็น enum มี `when others`
- [ ] การเทียบกับศูนย์ใช้ช่วงชัดเจน `(WIDTH-1 downto 0 => '0')` ไม่ใช่ `(others => '0')`
- [ ] ตัวเลขที่ต้องคำนวณใช้ `unsigned` / `signed` ไม่ใช่ `std_logic_vector`
- [ ] แปลง `std_logic_vector` ↔ `unsigned` / `signed` ที่ขอบของโมดูล

---

## 5. เช็กลิสต์ sequential logic

- [ ] ใช้ `<=` กับ signal และ `:=` กับ variable เท่านั้น
- [ ] ใช้ `rising_edge(clk)` ใน clocked process
- [ ] reset มีลำดับความสำคัญที่ประกาศไว้ชัดเจนในคอมเมนต์
- [ ] ทุกชั้นของ pipeline ถูกล้างเมื่อ reset
- [ ] ไม่มีการอ่านค่าที่เพิ่งถูก assign ในรอบเดียวกันโดยไม่ตั้งใจ
- [ ] ถ้าต้องการค่าถัดไป ใช้ variable คำนวณก่อนแล้ว assign ทีเดียว
- [ ] สัญญาณ flag ถูกกำหนดค่าในทุก path (ไม่ค้างค่าเก่าโดยไม่ตั้งใจ)
- [ ] ไม่มี combinational path ที่ตั้งใจให้เป็น latch โดยไม่มีคอมเมนต์อธิบาย

---

## 6. เช็กลิสต์ FSM

- [ ] ใช้ `enum` เป็นชนิดของสถานะ ไม่ใช้ `std_logic_vector`
- [ ] ทุก `case` ที่แปลงสถานะมี `when others`
- [ ] `when others` พาไปยัง safe state ไม่ใช่ปล่อยให้ค้าง
- [ ] มีทางออกฉุกเฉินสำหรับทดสอบ path กู้สถานะ
- [ ] รหัสสถาะที่ส่งออกไปยังบล็อกภายนอกตรงกับเวอร์ชัน Verilog
- [ ] ตัวนับบิตและตัวนับสถานะแยกจากกันชัดเจน

---

## 7. เช็กลิสต์การเชื่อมต่อและ clock domain

- [ ] สัญญาณข้าม clock domain มี 2-flop synchronizer ครบทุกเส้น
- [ ] synchronizer มี `attribute async_reg` กำกับ
- [ ] สัญญาณพัลส์สั้น ๆ ข้าม domain ใช้กลไก toggle หรือ FIFO ไม่ใช่ synchronizer ตรง ๆ
- [ ] handshake 4-phase รอให้ ack กลับเป็น 0 ก่อนเริ่มรอบใหม่
- [ ] ข้อมูลที่ส่งข้าม domain ถูกล็อกไว้นิ่งตลอดช่วงที่ handshake ยังไม่จบ
- [ ] เครื่องมือสังเคราะห์รู้จักว่าสัญญาณใดเป็น synchronizer (ผ่าน attribute หรือคำสั่งเฉพาะ)
- [ ] reset ของแต่ละ domain ถูกปล่อยให้เป็นจริงพร้อมกัน หรือมีวิธีจัดการที่ถูกต้อง
- [ ] พอร์ตข้าม domain ที่เป็นข้อมูลมีความกว้างที่ระบุไว้ชัดเจน

## 8. เช็กลิสต์ testbench

- [ ] เป็น self-checking จบด้วย marker `GOLDEN_<SHORT_ID>_PASS` หรือ `_FAIL`
- [ ] มี timeout watchdog ที่ตรวจ `done` ก่อนยิง TIMEOUT
- [ ] **นาฬิกาใน testbench หยุดเมื่อ `done` เป็นจริง**
      (`clk <= not clk after 5 ns when not done else '0';`)
- [ ] golden model เป็นการคำนวณอิสระ ไม่ได้เรียกฟังก์ชันหรือ RTL ของ DUT
- [ ] มี corner case: reset, ค่าขอบเขต, back-to-back, ค่า X, back-pressure
- [ ] ตรวจค่า X ก่อนแปลงค่าเป็นตัวเลข
- [ ] นับจำนวน error ใน `variable` และสรุปท้ายการทดสอบ
- [ ] ข้อความใน `report "..."` เป็น ASCII เท่านั้น
- [ ] ระบุเวลาในหน่วยเดียวกันทั้งหมด
- [ ] process ที่ไม่มี sensitivity list มี `wait;` ท้าย process เพื่อไม่ให้วนซ้ำ
- [ ] ใช้ `loop ... exit when ...` แทน `wait until` เมื่อรอสัญญาณที่อาจเป็นจริงอยู่แล้ว
- [ ] ถ้าอ่านไฟล์ stimulus ต้องใช้ `std.textio` (ไม่ใช้ `ieee.std_logic_textio`
      เพราะ GHDL ต้องการ `-fsynopsys` ในโหมด `--std=02`)
- [ ] พาธของไฟล์ stimulus ถูกระบุให้ชัดเจน และ testbench ล้มเหลวพร้อมข้อความที่เข้าใจได้
      เมื่อเปิดไฟล์ไม่ได้

## 9. เช็กลิสต์ก่อนส่งงาน

- [ ] คอมไพล์ผ่าน `--std=08`
- [ ] คอมไพล์ผ่าน `--std=02`
- [ ] testbench จำลองผ่าน ไม่มี assertion failure และเจอ marker
- [ ] `ghdl --synth` สังเคราะห์ผ่าน ไม่มี error
- [ ] ไม่มี warning ที่บอกว่ามี latch โดยไม่ตั้งใจ
- [ ] ไม่มี warning `no choice for ...` หรือ `cannot resolve overloading`
- [ ] ระบุเวอร์ชันของเครื่องมือที่ใช้ตรวจสอบ
- [ ] บันทึกคำสั่งที่ใช้ตรวจสอบลงใน README ของตัวอย่าง
- [ ] log การตรวจสอบถูกเก็บไว้ใน `reports/`
- [ ] ไม่มีข้อความที่อ้างว่า "ผ่าน sign-off" หรือ "ผ่านมาตรฐานโรงงาน"
- [ ] ไม่มีข้อมูลลับในโค้ดและใน log

คำสั่งตรวจสอบมาตรฐานสำหรับตัวอย่างหนึ่งตัว:

```bash
cd code/reference/vhdl
bash scripts/check_example.sh <example_id> <top_entity> <tb_entity>
```

และสำหรับทั้งชุด:

```bash
bash run.sh
```

## 10. เช็กลิสต์การทำงานร่วมกับ Verilog

- [ ] ชื่อ entity/module เหมือนกัน
- [ ] ชื่อพอร์ตและทิศทางเหมือนกันทุกตัว
- [ ] ความกว้างข้อมูลและค่าเริ่มต้นของ generic/parameter เหมือนกัน
- [ ] ลำดับความสำคัญของ reset และเงื่อนไขอื่นเหมือนกัน
- [ ] รหัสคำสั่ง (opcode, รหัสสถานะ FSM) ตรงกัน
- [ ] ความหมายของ flag (เช่น `carry_out` กับ `borrow_out`) ตรงกัน
- [ ] ทดสอบด้วย stimulus ชุดเดียวกันและเทียบสัญญาณทีละจุดเวลา
- [ ] ตรวจจุดต่างที่มักพบ 5 ข้อใน [บทที่ 14](14-verilog-cross-reference.md#72-จุดที่มักต่างกันเมื่อเทียบ)

## แบบฝึกหัดท้ายบท

1. สร้างสคริปต์ `scripts/check_style.sh` ที่ตรวจ BOM, trailing whitespace,
   ช่องว่างท้ายบรรทัด และฟีเจอร์ VHDL-2008 ที่ห้ามใช้ แล้วรันกับตัวอย่างทั้งชุด
2. เพิ่มข้อ 9.2 (การตรวจ latch โดยไม่ตั้งใจ) ให้สมบูรณ์ โดยหาจาก warning
   ของ `ghdl --synth` และอธิบายว่าอ่านข้อความนั้นอย่างไร
3. ตัดข้อ 8 ออกจากเช็กลิสต์ แล้วเขียนคำอธิบายว่าข้อไหนสำคัญที่สุด
   และเพราะอะไร
4. เพิ่มเช็กลิสต์สำหรับโค้ดที่จะส่งให้ลูกค้าภายนอก ซึ่งอาจต้องใช้มาตรฐาน
   VHDL-93 ล้วน ๆ แล้วอธิบายว่าต้องเพิ่มอะไร
5. ทำ checklist เวอร์ชันย่อสำหรับการแก้โค้ดของตัวเองในเวลา 10 นาที
   แล้วเทียบกับเวอร์ชันเต็มว่าตกอะไรบ้าง

## คำถามท้ายบท

1. ข้อใดในเช็กลิสต์ที่ตรวจได้ด้วยคำสั่ง และข้อใดที่ต้องอาศัยการอ่านโค้ด
2. ทำไม `ghdl --synth` ถึงเป็นเกณฑ์ที่จับ latch ได้ ทั้งที่การจำลองอาจไม่แสดงผล
3. ข้อ 8.9 (process ที่ไม่มี sensitivity list ต้องมี `wait;`) ป้องกันบั๊กอะไร
   และบั๊กนั้นแสดงอาการอย่างไร
4. ถ้าต้องเลือกเพียง 3 ข้อจากเช็กลิสต์ทั้งหมดที่ต้องทำเสมอ จะเลือกข้อใด
   และเพราะอะไร
5. ข้อ 10.6 (ทดสอบด้วย stimulus ชุดเดียวกัน) จับข้อผิดพลาดประเภทใดไม่ได้
